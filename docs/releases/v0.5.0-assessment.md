## Explicit numeric policy

The trusted SQL Server provider compiles approved numeric columns, literals, parsed strings and other numeric leaves to `decimal(28,6)` (or NULL if the source cannot be converted). Each **binary arithmetic** node narrows both operands with `TRY_CONVERT(decimal(19,6), ...)`, widens to `decimal(38,12)` for calculation, then uses `TRY_CONVERT(decimal(19,6), ...)` for the result. An out-of-range operand or result returns SQL NULL; division uses `NULLIF` for zero divisors. SQL WHERE follows ordinary three-valued logic, so NULL comparisons do not match. `decimal(19,6)` has at most 13 integral digits. Operands/outputs are rounded to six decimal places where conversion permits.

These limits apply per binary value node, including nested calculations. They are intentionally narrower than the leaf decimal type to prevent SQL intermediate overflow, and therefore **must be explicitly accepted as part of the v0.5 public semantics**. The editor and runtime binding UI reject values whose exact six-place decimal would be lost when converted to a JavaScript Number. The backend validates exact JSON decimals independently.

## Release decision and open items

- The checked-in package version is still **0.2.0** in `Directory.Build.props`. The v0.3, v0.4 and v0.5 work was merged incrementally without versioning individual packages; decide whether v0.5.0 is the next public package version and document the cumulative breaking/nonbreaking changes. Do **not** assume the website's v0.5 feature status is a published NuGet/GitHub Release.
- Confirm product acceptance of the new bounded-decimal arithmetic and its NULL-on-overflow behavior. This improves availability but can change truth values for extreme arithmetic that previously errored.
- SQL Server is the only executable provider here. Provider-neutral conversion behavior, strict financial precision beyond six places and production authorization/telemetry hardening remain future roadmap items.
- The published playground is a static editor. Actual validation, SQL compilation and data preview require the .NET API.
- Ensure PR and post-merge GitHub Actions are all green; review the release workflow and release notes before a separate version-bump/release PR.

**Decision:** Do not cut an automatic v0.5.0 GitHub/NuGet release from this correctness PR. Once the gates above and the intended numeric policy are accepted, publish through the normal audited version-bump release process, with release notes covering everything since v0.2.0.
